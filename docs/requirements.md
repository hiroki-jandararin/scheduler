## 0. 思想（プロダクトの軸）

> **予定を立てる・管理することに時間を使わない。でも、見やすい。**

本来やりたいのは「予定を立てること」ではなく「予定の中身をこなすこと」。だから、このアプリに触れている時間そのものを最小にする。

### デザイン原則

| # | 原則 | 具体的には |
|---|---|---|
| D1 | **入力は貼るだけ** | 予定作りはAIに任せる。アプリ側で一から入力させない。フォームの項目を埋める作業は作らない |
| D2 | **1ブロック1操作** | 日中に押すのは基本的に「完了」だけ。完了すると次のブロックが自動で始まる |
| D3 | **見ればわかる** | 開いた瞬間に「今なにをするか」「あと何分か」「何時に終わりそうか」の3つが分かる |
| D4 | **設定させない** | 初期値で困らないようにする。設定画面は最後まで作らないつもりでいる |
| D5 | **失敗しても直すのは一瞬** | 読み取りミスや押し忘れは、その場でワンクリックで直せる |

### 機能を足すときの判断基準
- その機能のために、ユーザーの**操作や入力が1つでも増える**なら、原則として入れない
- 入れる場合は、**使わない人には見えない**形にする（例：振り返りの詳細は折りたたむ）
- 迷ったら「これはタスクを立てる時間を減らしているか？」で判断する

## 1. 概要と目的

**一文で言うと**
AIと壁打ちして組んだ1日の予定を「貼るだけ」でタイムラインにし、日中の実行・予実の計測・振り返りまでを回せるアプリ。

**目的**
- AIで作った予定を、その日のうちに迷わず実行できる状態にする
- 予定と実績のズレを自動で数え、「自分の見積もりの甘さ」を数字で分かるようにする
- その数字を次の予定作りに戻し、だんだん現実的な1日を組めるようにする

**このアプリがやらないこと（設計方針）**
- AIによる予定作りはアプリの外（ユーザーが普段使っているChatGPT／Claudeなど）で行う
- アプリは「取り込み → 実行 → 計測 → 振り返り」に集中する

## 2. ペイン（解決したい課題）

| # | ペイン | 具体的な場面 |
|---|---|---|
| **P0** | **予定を立てる・管理すること自体に時間を取られる**（最重要） | ツールに入力し直したり、時間を調整したりで、やる前に疲れる。本当はすぐ作業を始めたい |
| P1 | AIで組んだ予定がチャットに流れて、日中に見返しにくい | 表をスクロールで探し直す。カレンダーへ手で移すのは面倒でやらない |
| P2 | 今何をすべきか、どれくらい押しているかが分からない | 1ブロックが延びても気づかず、後半の予定が崩れる |
| P3 | 見積もりが甘い自覚はあるが、どれくらい甘いか分からない | 毎回「9時間分」詰め込んで、終わらずに自己嫌悪 |
| P4 | 既存ツールは「重い」か「入力が面倒」 | TaskChuteは記録の作法が重い。カレンダーは実績が残らない。タイムブロックアプリは手入力か、アプリ内蔵のAIに頼ることになる |

## 3. ペルソナ

### メイン：本業＋個人活動を並行するエンジニア（＝自分）
- 20代後半、SESで働くバックエンドエンジニア
- 休日に「開発・発信（ブログ／ポッドキャスト）・学習・運動」とやりたいことが多い
- 予定はAIと壁打ちして組むのが当たり前になっている
- 計画を立てるのは好きだが、日中の実行と振り返りが続かない
- 欲しいのは「計画どおりにできたか」より「次にどう計画すればいいか」

### サブ
- **在宅のフリーランス・副業者**：自分で時間を組み立てる必要があり、予定と実績を見て単価や工数の感覚を養いたい
- **資格勉強中の社会人・学生**：学習時間を可視化したい。AIで勉強計画を作ることが多い

## 4. コンセプトと提供価値

**コンセプト：「AIが組んで、アプリが数える」**

| 提供価値 | 解決するペイン |
|---|---|
| 貼るだけで、その日の予定がタイムラインになる | P1, P4 |
| 「今」と「押し具合」が常に分かる | P2 |
| 予定と実績のズレを自動で数え、自分の見積もり倍率を出す | P3 |
| 見積もり倍率を「次にAIへ渡すプロンプト」として返す | P3（ループを閉じる） |

> 差別化の核：最後の「見積もり倍率をAIへ返す」部分。AI側は作るのが得意で、アプリ側は数えるのが得意。この往復を回せるのがこのアプリの価値。

---

## 5. 利用フロー

1. **前日（計画）**：アプリが用意した「推奨プロンプト」をコピーして、AIにやりたいことと一緒に投げる
2. **取り込み**：AIが返した予定をアプリに貼る → タイムラインに変換 → 必要なら微調整
3. **当日（実行）**：ブロックごとに「完了」を押す。押していれば後ろの予定をまとめてずらす（固定ブロックはずらさない）
4. **当日（組み直し）**：大きく崩れたらAIと組み直し、残りを貼り直す。それまでの実績は残る
5. **当日夜（振り返り）**：予実の一覧と、ズレ・見積もり倍率を見る
6. **次の計画へ**：「あなたは開発系を1.3倍で見積もると現実的」といった補正をプロンプトに含めてコピー → 1に戻る

## 6. 機能要件

### MVP（まず自分で2週間使える状態）

| ID | 機能 | 内容 |
|---|---|---|
| F1 | 予定の取り込み | テキストを貼り付けてパースする（6.3）。取り込み後にプレビューで確認・編集できる |
| F2 | 推奨プロンプト（任意） | AIに渡す短い一言をコピーできる。使わなくても取り込めることを前提にする |
| F3 | タイムライン表示 | 現在時刻のライン、今のブロックの強調、残り時間。PCの画面幅で1日全体が見渡せるレイアウト |
| F3-2 | ブロック種別 | 「作業」「休憩」（食事を含む）を区別して表示する。取り込み時にキーワードで自動判定し、手で変更もできる |
| F4 | 実行記録 | 基本操作は「完了」ボタンだけ。完了した時刻をそのブロックの終了・次のブロックの開始として記録し、次のブロックを自動で始める（D2）。最初のブロックだけ「開始」を押す |
| F4-2 | 記録の修正 | 押し忘れたときは、時刻をクリックして直せる（D5） |
| F4-3 | スキップ | 今のブロックと、まだ始めていないブロックをスキップできる。スキップしたブロックは終了見込みの計算と見積もり倍率から外し、振り返りには「スキップ」と表示する。今のブロックをスキップしたら、その時刻から次のブロックを始める |
| F5 | リスケ | 遅れが出たら、後続の予定を自動で後ろにずらして表示する。ユーザーの操作は不要。「何時に終わりそうか」を常に表示する（D3） |
| F5-2 | 固定ブロック | 「固定」の印が付いたブロックは予定どおりの時刻から動かさない。印は取り込み時にキーワードで自動で付け、プレビューやタイムラインでクリックして付け外しできる。前のブロックが固定ブロックに食い込みそうなときは、順番は入れ替えずに警告を出す（例：「15:00のMTGに20分食い込みそう」） |
| F6 | 日次の振り返り | ブロックごとの予定／実績／差分。見積もり倍率と誤差は、完了した**作業ブロック**（固定を除く）だけで計算する。休憩は「予定より何分延びたか」を別に表示する |
| F7 | データ保存 | ブラウザ内に保存（ログイン不要） |
| F8 | 日中の貼り直し | その日の予定がある状態で貼り直すと、完了・スキップ済みのブロックは残し、未着手のブロックだけを新しい予定に差し替える。進行中のブロックは続行し、新しい予定はその後ろに並べる。新しい予定のうち現在時刻より前に始まるものは取り込まず、プレビューに「過去の時間帯なので取り込まない」と表示する。最初に取り込んだ予定は別に保存しておく |

### ブロックの状態

```
pending（未着手） → active（進行中） → done（完了）
        └──────────────┴──────→ skipped（スキップ）
```

### リスケ（終了見込み）の計算ルール

- 保存するのは「予定の時刻」と「実際の時刻」だけ。ずらした後の予定は保存せず、毎回計算する
- 進行中のブロックは「実際の開始 ＋ 予定の所要時間」と「現在時刻」の遅い方で終わる見込みとする
- それ以降の固定でないブロックは、`max(前のブロックの見込みの終わり, 予定の開始)` から予定の所要時間で並べる。遅れは後ろへ押し出すが、早く終わっても予定より前には詰めない（早く終わったときに次がすぐ始まるのは、F4の自動開始で実現する）。予定にある空き時間は、遅れを吸収するために残る
- 残り時間は「実際の開始＋予定の所要時間 − 今」。予定を超えるとマイナスになり、「N分オーバー」と表示する
- 完了したとき、次のブロックが固定で、まだ予定の時刻になっていなければ自動では始めない（「開始」を押す）
- 固定ブロックは常に予定の時刻に置く。その後ろのブロックは固定ブロックの終わりから並べ直す
- スキップしたブロックは並べない

### 6.3 パース方式（確定：A＋D）

**セキュリティ上の前提**
- アプリ内でAIを動かさないので、プロンプトインジェクションの影響を受ける場所はない
- 貼り付けられたテキストは「信頼できない入力」として扱う
  - テキストはすべてプレーンテキストとして扱い、HTMLとして描画しない（XSS対策）
  - Markdownを解釈する場合も、リンクや画像、HTMLタグは無効にする
  - 上限：2万文字、500行、100ブロック。超えたら取り込みを中止して知らせる
  - `eval` やJSONの任意実行など、テキストをコードとして扱う処理はしない

**方式**
AIは使わず、正規表現とルールで1行ずつ読み取る純粋な関数として実装する。読み取り結果はプレビュー（D）で確認・修正してから確定する。

**処理の流れ**
1. **正規化**：全角数字・全角コロン・全角スペースだけを半角にする。NFKCは `開発①` を `開発1` に変えてしまうので使わない。ダッシュ類（`〜` `～` `ー` `–` `—` `−`）は置き換えず、時刻と時刻の間にあるときだけ区切りとして扱う（`アブローラー` の `ー` を壊さないため）。行頭の箇条書き記号、強調記号、表の区切り（`|` やタブ）を取り除く。表の区切り行と見出し行は読み飛ばす
2. **時刻範囲を探す**：`9:00-10:30` `9:00〜10:30` `9時〜10時半` `午後1時から2時` などを読み取る。数字だけの範囲（`9-10`）は誤検出が多いので対象外。1行に複数ある場合は最初のものを使う
3. **タイトル**：時刻範囲を取り除いた残り。所要時間の補足（`（1.5h）` `（60分）`）も取り除く
4. **種別と固定の推定**（キーワード）
   - 休憩：`休憩` `昼休み` `昼食` `ランチ` `朝食` `夕食` `食事` `仮眠` `入浴` `自由時間` `break` `lunch` など
   - 固定：`MTG` `会議` `打ち合わせ` `面談` `予約` `通院` `仕事` `勤務` `通勤` `帰宅` `確定` など
5. **全体の確認**：日付またぎ、12時間表記、時刻の矛盾を補正する

**補助ルール**

| 場面 | 処理 |
|---|---|
| 開始時刻だけの行（`9:00 朝会`） | 終了＝次のブロックの開始。最後の行で `就寝` `寝る` なら1日の終わりの印として扱い、ブロックにしない |
| 所要時間だけの行（`開発 2時間` `90分` `1時間半`） | 文書の中に時刻範囲の行が1つもないときだけ、所要時間モードにする。開始時刻から順に並べる。「合計」「計」を含む行は除外 |
| 所要時間モードの開始時刻 | 取り込む画面側で決める（今日なら現在時刻、明日なら9:00）。プレビューで変えられる。それより早い時刻の指定（`9時から買い物`）が文書内にあれば、その時刻から並べる |
| 所要時間モードの時刻指定 | 時刻の指定がある項目（`9時から買い物`）は固定ブロックとしてその時刻に置く。所要時間は仮に30分。ほかの項目は書かれた順に並べ、固定ブロックにかかる場合はその後ろに回す |
| 所要時間が書かれていない項目（`アブローラー`） | 所要時間の行に挟まれた短い行は、所要時間30分のブロックとして読み取り、プレビューで「所要時間が不明」と知らせる。文末が `。` の行は文章とみなして読み飛ばす |
| 12時間表記（`11:00-12:00` の次に `1:00-2:00`） | 前のブロックより時刻が戻っていて、時が12未満なら+12する |
| 日付またぎ（`23:00-1:00`） | 終了が開始より前なら翌日扱い |
| 読み取れない行 | 捨てずに「読み取れなかった行」としてプレビューに出す |

**テストの素材**
実際のAI出力を `src/parser/__fixtures__/` に置き、テストで使う。取りこぼしが見つかったら素材を足してからルールを直す。

## 7. 非機能要件・スコープ外

**非機能要件**
- PCのブラウザでの利用をメインにする。作業中に横に置いておけるよう、狭いウィンドウ幅でも見やすくする
- スマホは「確認できる」程度のレスポンシブ対応にとどめる
- 貼り付けてから使い始めるまで30秒以内
- ログイン不要で始められる。データはブラウザ内に保存
- 貼り付けたテキストは信頼できない入力として扱う（6.3を参照）

**技術構成**
- Vite＋React＋TypeScript。バックエンドは持たない
- 保存は localStorage
- テストは Vitest。パーサーとリスケ計算はTDDで作る
- デプロイは静的ホスティング（Cloudflare Pages など）

**スコープ外（やらないこと）**
- アプリ内でのAIによる予定作り（コストと差別化の両面で持たない）
- チームでの共有・管理
- ToDoやプロジェクトの管理（タスクの「置き場」にはしない）
- カレンダーとの双方向同期
- ブロックの順番の自動入れ替え（固定ブロックに食い込む場合も警告にとどめる）

## 8. 競合と差別化

| サービス | 強み | このアプリとの違い |
|---|---|---|
| TaskChute Cloud | 予実管理と振り返りが強い | 記録の作法が重く、慣れが要る。こちらは「貼るだけ」で始められる |
| Structured | 見やすいタイムライン、アプリ内AI、Replan | 予実の計測・見積もり倍率は弱い。AIはアプリ内蔵のものを使う |
| Googleカレンダー | 誰でも使っている | 実績が残らない。日中の運用向けではない |
| AIチャットそのもの | 予定を組むのは得意 | 日中の実行管理や、日をまたいだ記録・学習はできない |

**差別化ポイント**：「貼るだけ」の軽さ ×「数えて、AIに返す」ループ

## 9. 成功指標と検証計画

**成功指標（自分で使う段階）**
- 2週間のうち10日以上使う
- 貼り付けてから実行開始まで1分以内
- 2週目は1週目より、1日全体の見積もり誤差が小さくなる

**見積もり誤差の定義**
- ブロックごとの誤差 ＝ `|実績 − 予定| ÷ 予定`
- 1日の見積もり誤差 ＝ ブロックごとの誤差の平均
- 対象は、完了した作業ブロックだけ。休憩・スキップ・固定ブロックは除く
- 画面に出す「見積もり倍率」は別の指標（`実績の合計 ÷ 予定の合計`）。誤差は「ズレの大きさ」、倍率は「甘く見積もる癖の向き」を表す
- 10分未満の短いブロックをどう扱うかは、2週間分のデータを見てから決める

**検証ステップ**
1. **Web試作（11/15〜）**：F1〜F6の最小版を作り、明日の予定で1日回す
2. **自分で2週間使う**：続かなかった理由・面倒だった操作を記録する
3. **他の人に使ってもらう**：ポッドキャストの相方など2〜3人。ペルソナが合っているかを確かめる
4. 手応えがあれば、スマホ対応の強化や、有料にできる機能を検討する
